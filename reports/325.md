# 2026-11-12 — #325 Pi 400 network boot with #310 + the #332 fix (PR #356), Pi test agent

**Verdict: pass for Redox: 10 of 10 boots reached `redox login:`, with 4 CPUs
and no #332 fault** (before the fix: 2 of 6), and root logged in every time.

**Two problems before Redox starts:**

- **U-Boot's network load is unreliable on the Pi 400.** 5 of 11 boot
  attempts stopped at `U-Boot>` or had a failed load, and the first boot
  needed 2 retries by hand. Each time, typing `boot` again on the console
  worked. U-Boot's own `ping` to the server answers.
- **With the test card in the slot, the Pi 400 did not start at all.**
  Nothing came on the console after a reboot, so the EEPROM did not fall
  through to network boot. The user then took the card out and
  power-cycled.

- **Image:** `v0.5.0-dev-90-g92a6387c+x54e8` (`pi400-bringup` + `fix-332-tlb`,
  `--experiment pi400`), staged in `/srv/tftp/pi400`. The banner says
  `experiments: netstack-watch pi400`.
- **Setup:** Pi 400 serial console on ttyUSB1, log
  `~/redox-rpi/logs/serial-pi400.log`. No Shelly, so reboots were done with
  `reboot` from the console as root.
- **Firmware and U-Boot over the network:** EEPROM network boot (no card in
  the slot, U-Boot says `Card did not respond to voltage select`). U-Boot
  `2026.10 (Nov 10 2026)`, `DRAM: 947 MiB`, `RPI 400 (0xc03131)`. GENET
  `ethernet@7d580000`, DHCP 192.168.178.189. U-Boot fetches
  `netboot.scr` and the boot menu (`Network: pi400/`, `Network: stable/`).
- **Image over HTTP:** `redox-rpi: image loaded over HTTP`, 44753652 bytes
  in about 2 s when it works.
- **Kernel:** `gic: Distributor supports 4 CPUs and 256 IRQs`
  (`arm,gic-400`). Each of the 3 secondary cores reports `local SGI/timer
  self-test passed` and `online`, then `CPU activation complete: 4 CPUs
  online`, in every boot.
- **Login:** `root`, then `id` gave `uid=0(root) gid=0(root)` after every
  boot.

- **No #332 fault in any boot:** no `Not an SVC induced`, no `UNHANDLED
  EXCEPTION`, no panic. The redoxfs `data` mount fails (`/scheme/disk.mmc/0p1`,
  no EMMC2 driver in this image), as expected, and nothing faults after it.
- **The U-Boot load errors before Redox:**
  - The first power-up (before boot 1) stopped at `U-Boot>` twice: `HTTP
    client error 5` (no GET reached the server) and a TFTP `Loading:
    Timeout!`.
  - At the prompt, `ping 192.168.178.120` answered `is alive`. TFTP of the
    166 KB bootloader stopped after 6 blocks. One wget of the image failed
    with error 5 and the next loaded all of it in 2 s. Then `boot` worked.
  - Boot 7 had a different failure: TFTP of `netboot.scr` with `our IP
    address is <NULL>` (DHCP not done).
  - So U-Boot's GENET network fails at random, not every time. Sometimes a
    TCP connection opens but the request never arrives, and TFTP stalls
    after a few blocks. The server answered every request it got.
- **The card:** the user put the test card (redox-rpi-pi400-emmc2-testcard:
  p1 15 MiB empty non-FAT, p2 RedoxFS) into the Pi 400 after boot 2 had
  started.
  - Boot 3's `reboot` at 20:22:05 printed only `kreset`, then nothing: no
    firmware, no U-Boot. The Shelly cycle of the 3B+ at 20:23 did not touch
    it.
  - With the card out and a power cycle at 20:31:58, the Pi 400 network
    booted again, so boot 3 was counted from there.
  - So with this card in, the EEPROM stops on the SD card instead of
    trying network boot. That matters for row 363 part B.
- U-Boot also printed `Timeout waiting for cmd & data inhibit` 3× in some
  boots (EMMC with no card).
