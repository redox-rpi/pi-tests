## What it means

- The SET_IDLE change (base 0124) works: the mouse no longer stalls endpoint 0 at attach.
- The 5 s timeout (pi400 base 0021) now fires for a different request: about 7 s after the keyboard attached, the hub's own port-status request (`CUSTOM_DEVICE_REQ` on port 1, the VL805's hub) gets no answer.
  - xhcid times it out and returns `TimedOut`.
  - `usbhubd` treats that as fatal (`main.rs:234`, an `expect`) and aborts.
- The devices already attached keep working (three usbhidd). With usbhubd dead, though, there is no hotplug on the hub any more. A device plugged in later would not attach.
- In row 622 (row 501's image, same mouse), usbhubd also died at every boot, there at attach (`main.rs:136`, `Failed to address device … port 1.1`). With this image the mouse attaches, and usbhubd dies later instead.

Pointer movement and hotplug are not part of this row (they need a person).

Afterwards: row 501's image `v0.6.0-dev-105-gbef6d90a+xcf2a` staged and booted to the login (20:16).

- **Why Orbital did not start.** The boot log has `rpi-fbd: no EDID (no monitor, or the firmware does not read it)`, `rpi-fbd: no framebuffer: 1024x768: no answer from the firmware` and `vesad: No boot framebuffer`. In the first run, 15 minutes earlier, the firmware read `EDID 256 bytes, monitor HP 27 FHD` and gave 1824x984. So the monitor was probably off or asleep at this boot. config.txt for row 501 has no `hdmi_force_hotplug`. `/tmp/desktop.log` was lost with the restore reboot. To check step (3) again, the monitor must be on, or the row can use the 584/610 config.
- **xhcid thread count.** `ps` lists 26 xhcid threads (6 in the first run), the same at 3 min and at the end, so they do not keep growing. Possibly one per retried status request; Graphics may want to look.
