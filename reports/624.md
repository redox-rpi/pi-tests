## Step 5 – what the agent saw

**USB at boot:**
- the mouse on port 1.1: usbhidd pid 49, `USB Optical Mouse`
- the built-in keyboard on port 1.4, interface 0: usbhidd pid 52
- the built-in keyboard on port 1.4, interface 1: usbhidd pid 53

**At the unplug (03:16.9 after boot):**
- `xhcid … EXECUTE_TRANSFER transfer Trb { data: 000000000AF22000, status: 00200004, control: 00000425 } failed with event Trb { data: 00000000054FC060, status: 24000004, control: 02038001 }` (completion code 0x24, slot 2, endpoint ID 3)
- usbhubd `port 1 status … CONNECTION_CHANGED | RESET_CHANGED`
- `killing driver process 49 for port 1.1` / `killed driver process 49`

**At the replug (03:30.2):**
- usbhubd connects, resets and `attach port 1.1`
- a new usbhidd, pid 86, starts for the `USB Optical Mouse`
- no `timed out` and no error after that

**ps after the replug** (15:36:32, 15:37:06–37, 15:38:34 UTC; [files](624/)):
- usbhubd running.
- 3 usbhidd: 52 and 53 (keyboard), 86 (new mouse). xhcid has 7 threads.
- **usbhidd 52 (keyboard interface 0) stays at exactly 17.68 s user + 18.12 s system in all samples over 2 minutes.**
  - That process carries the known #715 idle spin (Test 637: usbhidd 6.5–10.5 % at idle), so before the unplug its time kept growing.
  - **After the unplug it no longer runs at all. The keyboard driver seems stuck (blocked)**, which fits the lost keys.
- CPU over 8–13 s after the replug: the whole system under 1.5 % per process (rpi-firmwared 1.1–1.3 %, others below 1 %).
  - The "slower" the user saw was not CPU load.
  - It may have been input stuck in the keyboard path.
