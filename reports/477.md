# 477: `chain A N 1` (SDRAM reset) with the GCC build: chain path or TCC build?

**Result: the GCC build G hangs exactly like T did in Test 476 C.** After `ok chain 32032 bytes, start 0x80000200, SDRAM reset` nothing came for 120 s: no banner, no `[sdram]` lines, no monitor prompt. So the hang comes from **the chain path with SDRAM reset** (the selector's `chain … 1` and its trampoline), **not from the vc4-tcc build**.

- Pi 3B+, selector card in, no person, nothing on the card changed. 2026-11-17, 06:37–06:41 UTC.
- Payload G from Test 476: `~/rbc-build/payloads/bootcode-gcc-rel01-22bbd72-20261117.bin`, 32 032 bytes, sha256 `0f68733b6037…`, crc32 7FE6BB71.
- **How:** power cycle, the selector's monitor (233c8c5), `l c1000000 7d20 7FE6BB71` (with `rbc-load.sh --enter … none`), then `chain c1000000 7d20 1` typed as one line.

```
SDRAM ready after 50957 us
ok monitor
rbc> l c1000000 7d20 7FE6BB71
ok send 32032 bytes as hex
ok crc32 7FE6BB71
rbc> chain c1000000 7d20 1
ok chain 32032 bytes, start 0x80000200, SDRAM reset
```

That is the last line. G never printed its banner (`redox-rpi bootcode 22bbd72 …`), so `sd`, `fl START.ELF` and `crc` could not run.

| | Test 476 C (T, vc4-tcc) | Test 477 (G, GCC) |
|---|---|---|
| `l` | `ok crc32 2E4926DC` | `ok crc32 7FE6BB71` |

| after that, 120 s | nothing | nothing |

The same G chained without the `1` (Test 476 A, `SDRAM running`) started at once and passed every command. That fits the firmware session's suspicion: the trampoline copies the image through the cached alias while SDRAM is being taken down.
