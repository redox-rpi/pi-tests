# Test 560 – does `ls /scheme/` hang because of the still-mouse xhcid bug? (Pi 400, #592 / PR #594)

Date: 2026-11-21. Pi test agent. Run after the user had restarted the Pi 400 from the Test 558 hang. USB mouse plugged in and not touched. Both stages pass `sha256sum -c SHA256SUMS`.

Result: **pass, as expected**:
- **B** (with 0019/0020) returns from `ls /scheme/`.
- **A** (before the fix) hangs there, the same way Test 558 B did.

**Order:** B ran first (15:13), then Test 561 B, then A last (15:29). A was expected to leave the console stuck, and that would have blocked 561 B until a person restarted the Pi 400 again.

## B – `v0.6.0-dev-127-g5e48dca1+x1cc4-dirty` (with 0019, 0020)

- `USB HID driver:` "USB Optical Mouse" and both "Raspberry Pi Internal Keyboard" interfaces. `ps | grep -c usbhidd` → 6 (the usb-trace lines are mixed into the output).
- 30 s after login, **`ls /scheme/` returned at once** and listed the schemes ([B-ls.log](560/B-ls.log)).
- `ls /scheme/ | wc -l` → **38**; `cat /scheme/sys/uname` → `Redox 0.5.12 aarch64 c951af42…` ([B-more.txt](560/B-more.txt)).
- My script first said "did not return". That was wrong: the serial helper was killed by its timeout before it printed, while the list was already in the log. The console still answered (`echo` worked). I fixed the check (it now looks for the list in the log), and 561 B and A used the fixed check.
- 0 `RELIBC PANIC`, 0 `UNHANDLED`, 0 `panic`.
