# Test 591 – stale ARP entry during a busy TCP connection, A/B (#140, PR #463), Pi 3B+

Date: 2026-11-24, 08:24–08:47 UTC. Pi test agent, no person. Stage `~/zrtl-q/arp591-stage/` (`sha256sum -c SHA256SUMS` all OK). A: main `v0.7.0-dev-25-g8d245cc4+xa91e`. B: main + PR #463 `v0.7.0-dev-27-g4ba4cc78+xa91e`. Both have the experiments `usb-port-power` and `netstack-watch`.

Result: **pass, with a limit.** B shows no pause over 0.5 s in 2 × 150 s of streaming, and no extra resends at 60 s or 120 s. **A does not show the pause on the real Pi either.** Here the peer answers ARP at once, so the slow-ARP case from QEMU (1.5 s) does not come up. This test cannot tell A and B apart.

## How it was run (not `test-tcp-arp.sh`)

`test-tcp-arp.sh` and `tcp-arp-check.py` from the row only work in QEMU: they start QEMU with a socket netdev and play a peer that answers ARP after 1.5 s. They cannot be pointed at the Pi. A slow ARP peer on the real network would need raw sockets on the build host (a host change), so I did not try that.

Instead, as close as possible without host changes:
- A small sender on the build host ([arpsend.py](591/arpsend.py)) streams to the Pi for 150 s.
- On the Pi, `nc <build-host>:5591 < /scheme/null > /scheme/null` reads it, so the Pi only sends ACKs, as in the QEMU test.
- The sender logs every `send()` that blocks for more than 0.5 s. When the Pi holds its ACKs back, the send buffer fills and `send()` blocks.
- The sender also logs TCP retransmits per second from the kernel's `TCP_INFO`.
- Each image ran 2 streams; stable ran 1 stream for reference.

- Around 60 s and 120 s (seconds 55–68 and 115–128) the throughput and the retransmits per second look like every other second, in A and in B. There is no dip and no burst of resends.
- **A finding outside this row:** every run, stable included, has a steady ~113 retransmits per second, about 1.4 % of the segments (about 7900 segments/s at 11.5 MB/s). These are packets from the build host that the Pi did not acknowledge in time. They are the same in A, B and stable, so they do not come from PR #463. They look like receive losses in the LAN7800 path (dwc2d or the driver). Worth an issue for the Network session.
- The boots of A and B came up with the USB port on the first try (`usb-port-power`). Stable (no `usb-port-power`) needed two serial resets (#576) before devsh answered.

## What is still open

The real-Pi run cannot reproduce the slow-ARP case, so it says only this: PR #463 makes no change for the worse on a normal network (B is as fast and as steady as A). The QEMU run with the delayed-ARP peer is still the test that shows the fix. To see it on the Pi, a peer that answers ARP late would be needed: a second machine, or the build host with raw sockets (a host change through HomeNodeLLM).
