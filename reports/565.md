# Test 565 – why ipv6 takes no router advertisement on the Pi 3B+ (diagnosis)

Date: 2026-11-21. Pi test agent. Image `v0.6.0-dev-133-g9b1ce300+x0a9d` (Test 563 A, `~/zrtl-q/ipv6b-3bp-stage/`). No pass/fail; no panic.

## Short answer

- **IPv6 multicast passes the hash filter.**
- With the filter on and with it off, the result is the same: the Pi takes the **ULA prefix** `<ula-prefix>::/64` about 3 minutes after boot.
- It gets no global address and no IPv6 default route, but the LAN offers neither right now (see the correction below): **the Pi takes what the LAN offers.**
- So the filter is not the cause, and there is no missing piece in the RA handling that this test could show.
- (Test 563 A looked only 60 s after login, before the first ULA RA came.)

## Run 1 (as in the row)

- First boot: no devsh. One serial reboot fixed it; that is the Test 562 USB fault, not IPv6.
- **(1)** About 60 s after login, `addr/list` showed `<lan-ip>/24` and `fe80::<pi-iid>/64` only ([1-addr.txt](565/1-addr.txt), [1-netdiag.txt](565/1-netdiag.txt)).
- **(2)** ICMPv6 echo from the build host to `fe80::<pi-iid>%<lan interface>`: **3/3 replies** (0.5–0.6 ms). Neighbour discovery through the solicited-node group passes the filter.
  The host has no `ping` binary, so this used the Python ICMPv6 socket tool, now with link-local scope support.
- **(3)** Filter on, `addr/list` every 60 s for 12 min:
  - minutes 1–2: only link-local;
  - **minute 3 (14:49:36): `<ula-prefix>:0:<pi-iid>/64` appears**, and stays through minute 12;
  - no `<global-addr>` address at any time.
- **(4)** The row's command `echo -n all > /scheme/network.usb/multicast` failed: `No such device (os error 19)`. In this image the scheme is called **`network.usb_lan78xx`** (netdiag shows `network.usb_lan78xx/adapters 1`). So step 4 of run 1 is not valid ([4-filteroff.txt](565/4-filteroff.txt)).
  The 12 minutes after it look the same as step 3.
  End: `route/list` has `<ula-prefix>::/64 dev eth0`, `fe80::/64`, `ff00::/8`, and **no IPv6 default**. Link-local ping 3/3.

## Run 2: step 4 with the right path

To finish the row, I ran step 4 again in a second boot ([565/step4-rerun/](565/step4-rerun/)):

- `ls /scheme/network.usb_lan78xx` → `echo -n all > /scheme/network.usb_lan78xx/multicast` worked, and the serial log shows `dwc2d: LAN7800 multicast filter off, all multicast`.
- Then every 60 s for 12 min:
  - minutes 1–2: only link-local;
  - **minute 3: the same ULA appears**;
  - **no global address, no IPv6 default route** after 12 minutes (same `route/list` as run 1).
- Link-local ping 3/3.

## What the LAN offers (correction from the Network session)

My first reading of the build host's routes was wrong. The build host itself has **no global IPv6 address and no IPv6 default route** right now. Its only non-link-local addresses are in the ULA prefix (`<ula-prefix>::/64`). (It does show some `proto ra` prefix routes for a global prefix via other routers' link-local addresses, but no address or default route from them.)

**So the Pi got exactly what the LAN offers**: the ULA address and its on-link route. It did not miss a global address or a default route. Test 563 A's "no global address, no default route" is the LAN, not the Pi. The one real Pi-side finding of 563 A is that the ULA comes only about 3 minutes after boot (the first unsolicited RA), not within the 60 s that 563 A waited.

No `RELIBC PANIC`, no `UNHANDLED EXCEPTION`, no `panic` in either run. Afterwards stable `v0.6.0-dev-115-gb972ccfd+x2d42` was staged and booted, and devsh is up.
