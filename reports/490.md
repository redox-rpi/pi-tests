# 490: fast serial input with `serial-rx2` (#481 REQ-CON-2 / #28, PR #547), Pi 3B+

**Result: fails as written. 20 of 20 was missed (19), and the 100-line runs got 97 and 96 of 100. But no characters were lost anywhere.** Every line the test marked "LOST" is in the console log complete and byte-identical to the lines it marked "complete". `rx_overruns` stays 0 in every reading, the stash never fills, and `rx_bytes` matches the bytes sent (within 1 byte). pi-test passes 6/6. Most likely the "lost" lines came late, not short. The test waits only 30 s for each echo, and the shell redraws the whole line for every character it reads: about 31 KB of console output for each 209-byte command.

**Main finding: no lost line comes with a rise in `rx_overruns`. It is 0 in all 5 readings.**

Byte count: each command is `echo ` + tag + 200 characters + CR = 209 bytes. On top of that come the 21-byte `cat /scheme/sys/uart` + CR, and 2 bytes (Ctrl-U, CR) for each LOST tag:
- B1 20: 4 254 − 51 = **4 203** received; 20×209 + 21 + 2 = **4 203** expected.
- B1 100: 25 182 − 4 254 = **20 928**; 100×209 + 21 + 6 = **20 927**.
- B2 100: 20 981 − 51 = **20 930**; 100×209 + 21 + 8 = **20 929**.

So the driver got every byte (the 1-byte excess is probably an extra CR from `sercmd.py`).

### The "lost" lines are complete in the console log

For S15 (B1), S38/S39 (B2) and the neighbours S14/S16, I took the output line from `serial.log` and ran the test's own check on it (`tr -d '\r\000' | grep -x "$tag$LINE"`). **All match exactly.** The echo and redraw block before each output line has the same size (31 310 bytes) for a "complete" tag (S14, S16) as for a "LOST" one (S15, S38). So the shell read and ran every line complete.

What remains is time. The shell redraws the prompt and the whole line for each character, which is about 31 KB per line, at least 2.7 s at 115 200 Bd. A run of 100 lines took 16–18 minutes, about 10 s per line. A line counts as LOST when its output isn't in the log after 30 checks one second apart. The log has no timestamps, so I can't show the delay of each line. A rerun with a longer wait, or with `tsl.py` timestamps, would settle it.

That is also why the stable image "loses" lines (A 100: 2), and serial-rx2 is no worse than chance there. The ratings above only cover the delay, not lost data.
