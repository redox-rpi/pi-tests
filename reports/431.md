## New finding: `pressed` reaches the window only with the next event

The user: "when I press up there is no event; all events come only when I let go", and "the app only shows `released`". The serial log with `/tmp/dwc2d-input-log` shows dwc2d itself sends at once, with the first held report:

```
      1 R 7f 00            <- first report with UP held
      1 axis 0x31 32767
      1 button 0x90 pressed  <- dwc2d sends pressed here
    231 R 7f 00            <- 231 more reports while held
      1 R 7f 7f
      1 axis 0x31 0
      1 button 0x90 released
```
(`R` = raw D-pad bytes 4–5; counts from `uniq -c`.) In a live check at 19:44:25 the raw state was UP held (a run of 283 reports), while `/tmp/gp.log` still had 0 events. The `pressed` line appeared only after the release, right before `released`. So the delay sits after dwc2d: in Orbital's delivery to the window, or in gamepad-test's event loop, which seems to wake only on the following event. This also explains what the user called "not very reliable": the box only flashes, and short presses look lost.

## 8BitDo Micro (extra)

The user had switched the Micro to another mode; hotplugged after the DragonRise:
```
dwc2d:     address 5: 2dc8:9020, USB 2.00, class 0x00, Full speed
dwc2d:       interface 0 alt 0: class 0x03 subclass 0x00 protocol 0x00
dwc2d:         endpoint 0x81: interrupt max packet 64
dwc2d:         endpoint 0x02: interrupt max packet 64
dwc2d: request [81, 06, 00, 22, 00, 00, 88, 00] to address 5 (max packet 64, Full speed) failed: Stall
```
In this mode it is a plain HID interface (no boot protocol) with an OUT endpoint, likely the gamepad mode. But **the report-descriptor request (136 bytes) stalls**, so dwc2d never sees it as a gamepad. Row 416's mode was `2dc8:9021` (boot keyboard + mouse). The same stall shows on stable when the Micro is plugged in at boot.
